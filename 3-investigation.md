# Investigation report - source trace (2026-09-20)

## Status and evidence boundary

No RPCS3 or HindsightVR code was changed during this investigation.

The RPCS3 observations below were checked against the local `rpcs3` checkout at
commit `9e86f165d1711b9429d48b0487e7bc5ba0cc9c6c` (2026-09-19). Evidence labels
follow the local VR modding playbook:

- `[SOURCE]` - directly verified in the checked-out source.
- `[AUTHOR]` - a claim or method documented by HindsightVR's authors.
- `[INFERENCE]` - a proposed interpretation or experiment which still needs runtime proof.
- `[LIVE]` - observed at runtime. The only live evidence currently in scope is the
  user-reported WipEout native-3D result; it was not independently reproduced in this pass.

## Intended product architecture (normative)

The target is **not** to use WipEout's native 3D mode as the shipping render path.
That mode is generated by the game and runs at 30 fps. It is valuable only as a
known-good stereo oracle.

The intended path is:

```text
WipEout ordinary 2D mode at 60 fps
  -> one guest simulation frame
  -> one RSX command/draw stream
  -> identify and classify world draws
  -> preserve the draw's original guest state
  -> create transient left- and right-eye camera constants
  -> render the selected geometry into two host eye targets
  -> handle HUD/2D/post-process draws according to their class
  -> later submit the two generated eyes through OpenXR
```

"From the same guest frame" means stereo amplification at the draw/geometry level.
It does **not** mean forwarding the game's 30-fps frame-packed output, running two
guest simulation frames, or synthesizing depth by shifting pixels in the resolved
2D image. The two views must be independently rasterized from the same guest geometry
with eye-correct camera transforms so that occlusion and parallax are genuine.

The native-3D route has three bounded jobs in this project:

1. reveal which program families, constants, passes, and targets change between eyes;
2. provide expected disparity, sign, scale, convergence, and HUD behavior;
3. validate that the new 2D/60-fps stereo amplifier produces equivalent geometry.

## Executive result

1. `[SOURCE]` RPCS3 does not synthesize the two cameras used by a native PS3 3D
   game. It advertises PS3 3D display modes and records the guest's selected video
   mode. WipEout is responsible for rendering the two views. Consequently, the
   existing path is a reference oracle, not reusable 60-fps stereo generation.
2. `[SOURCE]` For the 720p frame-packed mode, the guest-visible output is
   1280x1470: 720 lines for one eye, a 30-line spacer, and 720 lines for the other.
   The Vulkan presenter resolves one combined image or two images at the two guest
   addresses and then converts them to the selected host output mode, including SBS.
3. `[SOURCE]` There is no current per-draw RSX eye state. The `eye` field in
   `present_surface_info` is assigned only during presentation and is not consumed
   by draw processing. Per-draw eye ownership must initially be `unknown` and
   inferred from render-target provenance and repeated draw structure.
4. `[SOURCE]` The most reliable inspector seam is `VKGSRender::emit_geometry()`
   after draw dependencies and vertex upload have succeeded, but before the Vulkan
   draw is emitted. An upload-only hook would miss draws which reuse an unchanged
   constant allocation.
5. `[SOURCE]` RPCS3 already exposes the two most valuable Tier-2 hunt inputs:
   original guest constant indices used by a vertex program (`constant_ids`) and
   whether the shader dynamically indexes the constant bank
   (`has_indexed_constants`).
6. `[INFERENCE]` The first patch should capture evidence only. Candidate
   perturbation belongs in a second, separately gated patch after WipEout's paired
   passes and candidate constants have been identified. The subsequent renderer
   milestone is to amplify the 2D draw stream into two host views; the native presenter
   is not that renderer.

## 1. PS3 stereoscopic configuration and video state

### Host configuration

- `[SOURCE]` `rpcs3/rpcs3/Emu/system_config.h`, `cfg_root::node_video`:
  `stereo_enabled` is serialized as `3D Display Enabled`; `stereo_render_mode` is
  serialized as `3D Display Mode`.
- `[SOURCE]` `rpcs3/rpcs3/Emu/system_config_types.h`,
  `video_stereo_render_mode`: the presentation choices are disabled, side-by-side,
  over-under, interlaced, red/cyan anaglyph, and green/magenta anaglyph.
- `[SOURCE]` `rpcs3/rpcs3/rpcs3qt/settings_dialog.cpp` exposes these as host
  presentation settings.

The host setting and the guest's active mode are distinct. `g_cfg.video.stereo_enabled`
allows RPCS3 to advertise 3D support. `rsx::avconf::stereo_enabled` becomes true only
after the guest actually selects a 3D resolution.

### Guest-visible modes

- `[SOURCE]` `rpcs3/rpcs3/Emu/Cell/Modules/cellVideoOut.cpp`,
  `_IntGetResolutionInfo()`: ordinary 720p is 1280x720; the principal 720p 3D
  frame-packing mode is 1280x1470.
- `[SOURCE]` `cellVideoOutGetDeviceInfo()` and
  `cellVideoOutGetResolutionAvailability()` advertise the frame-packing modes only
  when host 3D support is enabled and the configured base output is 720p.
- `[SOURCE]` `cellVideoOutConfigure()` rejects a 3D resolution when host support is
  disabled, then writes `resolution_id`, `stereo_enabled`, aspect, format, pitch,
  width, and height into `rsx::avconf`.
- `[SOURCE]` `rpcs3/rpcs3/Emu/Cell/Modules/cellAvconfExt.cpp`,
  `cellVideoOutGetScreenSize()`, reports the configured PS3 3D display size when
  stereo is enabled.
- `[SOURCE]` `rpcs3/rpcs3/Emu/RSX/Utils/rsx_utils.h`, `rsx::avconf`, is the shared
  video configuration object. `rsx_utils.cpp`, `avconf::video_frame_size()`, turns
  a 1280x1470 packed mode into an individual 1280x720 eye size with
  `(resolution_y - 30) / 2`.

`rsx::avconf::stereo_enabled` is therefore frame/output state, not a draw-time eye
selector.

## 2. How the native PS3 stereo oracle reaches Vulkan presentation

The verified path is:

```text
host enables PS3 3D capability
  -> cellVideoOut advertises frame-packing resolutions
  -> WipEout selects a 1280x1470 mode
  -> cellVideoOutConfigure updates rsx::avconf
  -> WipEout renders its own left/right views into guest RSX memory
  -> VKGSRender::flip resolves the packed output
  -> video_out_calibration_pass repacks it as SBS/OU/interlaced/anaglyph
```

### Present-source resolution

- `[SOURCE]` `rpcs3/rpcs3/Emu/RSX/VK/VKPresent.cpp`, `VKGSRender::flip()`, reads the
  active display buffer and `rsx::avconf`, then constructs a
  `present_surface_info` for the first 1280x720 eye.
- `[SOURCE]` If stereo is active and that image does not already cover the combined
  packed surface, it resolves a second guest address:

  ```text
  display_buffer.offset + (eye_height + 30) * display_buffer.pitch
  ```

  It otherwise keeps the one combined frame-packed source.
- `[SOURCE]` `VKGSRender::get_present_source()` resolves the guest address through
  the render-target surface store, texture cache, or a memory upload.
- `[SOURCE]` `rpcs3/rpcs3/Emu/RSX/VK/VKGSRenderTypes.hpp`,
  `present_surface_info::eye`, is set to 0/1 in `flip()`. The current tree has no
  consumer of this member outside presentation, so it cannot classify earlier draws.

### Host stereo conversion

- `[SOURCE]` `VKGSRender::flip()` passes one or two resolved sources to
  `vk::video_out_calibration_pass`.
- `[SOURCE]` `rpcs3/rpcs3/Emu/RSX/VK/VKOverlays.cpp`,
  `video_out_calibration_pass::run()`, supplies presentation mode, image count,
  and anaglyph matrices and binds up to two image views.
- `[SOURCE]` `rpcs3/rpcs3/Emu/RSX/Program/GLSLSnippets/VideoOutCalibrationPass.glsl`
  performs the final sampling. It can split one packed image or combine two images
  into SBS, over-under, interlaced, or anaglyph output.
- `[SOURCE]` `rpcs3/Utilities/stereo_config.cpp` selects the output mode only
  while the guest video configuration is stereo-enabled.

This is presentation composition, not stereo geometry generation. The native
left/right camera transforms were already applied by WipEout's RSX draws. This path
documents the oracle and may later supply comparison captures, but it is not the target
VR delivery path.

## 3. RSX command to Vulkan draw trace

```text
rsx::thread::on_task()
  -> rsx::thread::run_FIFO()
     -> decode method register
     -> methods[reg](context, reg, value)
        -> NV4097_SET_BEGIN_END / nv4097::set_begin_end()
           -> VKGSRender::begin()
              -> init_buffers(context_draw)
                 -> prepare_rtts()
           -> draw-array/index/inline methods build current_draw_clause
           -> VKGSRender::end()
              -> analyse_current_rsx_pipeline()
              -> load_program()
              -> load_program_env()
              -> emit_geometry(sub_index)
                 -> apply draw-clause dependencies
                 -> upload/validate vertex data
                 -> update_vertex_env()
                 -> bind program and draw state
                 -> vkCmdDraw* / vkCmdDrawIndexed*
```

Exact source owners:

- `[SOURCE]` `rpcs3/rpcs3/Emu/RSX/RSXThread.cpp`, `rsx::thread::on_task()`, runs the
  FIFO loop.
- `[SOURCE]` `rpcs3/rpcs3/Emu/RSX/RSXFIFO.cpp`, `rsx::thread::run_FIFO()`, reads and
  decodes methods and invokes `methods[reg]`.
- `[SOURCE]` `rpcs3/rpcs3/Emu/RSX/rsx_methods.cpp` maps
  `NV4097_SET_BEGIN_END` to `nv4097::set_begin_end()`.
- `[SOURCE]` `rpcs3/rpcs3/Emu/RSX/NV47/HW/nv4097.cpp`:
  `draw_arrays()`, `draw_index_array()`, and `draw_inline_array()` populate
  `current_draw_clause`; `set_begin_end()` calls the renderer's `begin()` and
  `end()` around the compiled clause.
- `[SOURCE]` `rpcs3/rpcs3/Emu/RSX/VK/VKDraw.cpp`, `VKGSRender::begin()`, initializes
  render targets. `VKGSRender::end()` selects programs and constant state and calls
  `emit_geometry()` for each RSX subdraw. `emit_geometry()` issues the Vulkan draw.
- `[SOURCE]` Base `rsx::thread::end()` increments the logical RSX draw-call count
  after the backend draw has completed.

A single logical RSX begin/end clause can produce several `emit_geometry()` calls
and an emitted subdraw can issue more than one `vkCmdDraw*`. The inspector must keep
both a logical `rsx_draw_ordinal` and `subdraw_index`; a Vulkan-command count should
be included rather than pretending these concepts are identical.

## 4. Render-target identity and native-eye provenance

- `[SOURCE]` `rpcs3/rpcs3/Emu/RSX/RSXThread.cpp`,
  `rsx::thread::get_color_surface_addresses()` and
  `get_zeta_surface_address()`, resolve RSX offsets/DMA locations to guest addresses.
- `[SOURCE]` `rsx::thread::get_framebuffer_layout()` snapshots clip dimensions,
  color and depth addresses, pitches, formats, anti-aliasing, target selection, and
  color-write masks.
- `[SOURCE]` `rpcs3/rpcs3/Emu/RSX/VK/VKGSRender.cpp`,
  `VKGSRender::prepare_rtts()`, passes that layout into
  `m_rtts.prepare_render_target()`, binds the Vulkan render targets, and records
  address/pitch in `m_surface_info`.

The stable semantic identity for a capture is the guest color/depth address plus
layout and capture-frame generation. A Vulkan image/view handle may be logged for
diagnostics, but it is neither stable across runs nor a semantic eye identifier.

`[INFERENCE]` For the final display buffer, an address overlap can label a target as
`top_eye_range`, `bottom_eye_range`, `combined_frame_pack`, or `no_direct_overlap`.
That label must remain an inference: WipEout may render eyes through offscreen targets
before compositing, and target reuse can make address-only labels ambiguous.

## 5. Vertex programs and transform constants

### Guest constant state

- `[SOURCE]` `rpcs3/rpcs3/Emu/RSX/rsx_methods.h`, `rsx::rsx_state`, stores
  `transform_program` and a 512-entry `transform_constants` array. RSX programs use
  the first 468 `vec4` entries.
- `[SOURCE]` `rpcs3/rpcs3/Emu/RSX/NV47/HW/nv4097.cpp`,
  `set_transform_constant::{decode_one,batch_decode,impl}`, writes the guest register
  bank and marks it dirty only when values change. Constant changes inside a draw
  clause become dependency barriers.

### Program translation and fetch maps

- `[SOURCE]` `rpcs3/rpcs3/Emu/RSX/RSXThread.cpp`, `prefetch_vertex_program()`, calls
  `program_hash_util::vertex_program_utils::analyse_vertex_program()` over the RSX
  microcode. `get_current_vertex_program()` adds current output/control/texture state.
- `[SOURCE]` `rpcs3/rpcs3/Emu/RSX/Program/ProgramStateCache.cpp`,
  `analyse_vertex_program()`, follows control flow and constructs the normalized
  `RSXVertexProgram` and instruction mask.
- `[SOURCE]` `rpcs3/rpcs3/Emu/RSX/VK/VKProgramBuffer.h`,
  `VKTraits::recompile_vertex_program()`, invokes `VKVertexProgram::Decompile()`.
- `[SOURCE]` `rpcs3/rpcs3/Emu/RSX/Program/VertexProgramDecompiler.cpp`, `GetSRC()`,
  records every statically addressed original guest constant in `m_constant_ids` and
  marks `has_indexed_constants` for address-register indexing. `BuildCode()` compacts
  static constants for the translated host shader while retaining the original index map.
- `[SOURCE]` `rpcs3/rpcs3/Emu/RSX/VK/VKVertexProgram.cpp` declares the constant
  buffers and emits the Vulkan GLSL vertex program. Its generated main applies
  RPCS3's viewport and clip conversion after the translated guest program result.

The inspector must report original RSX indices, `c[0]..c[467]`, not the compacted
Vulkan positions.

### Upload and per-draw selection

- `[SOURCE]` `rpcs3/rpcs3/Emu/RSX/Core/RSXDrawCommands.cpp`,
  `draw_command_processor::fill_vertex_program_constants_data()`, copies either the
  shader's statically referenced original guest constants or the full bank for an
  indexed program.
- `[SOURCE]` The instancing sibling, `fill_constants_instancing_buffer()`, replays
  mid-clause constant updates and creates per-instance data. It is a separate path
  which any later perturbation implementation must cover.
- `[SOURCE]` `rpcs3/rpcs3/Emu/RSX/VK/VKGSRender.cpp`,
  `VKGSRender::load_program_env()`, allocates and fills a ring-buffer region only
  when constant state is dirty, then associates it with the vertex-program binding.
  `upload_transform_constants()` performs the ordinary copy.
- `[SOURCE]` `VKGSRender::update_vertex_env()` writes the selected
  `xform_constants_offset` into per-draw parameters. `patch_transform_constants()`
  can allocate a replacement region for mid-pass changes.

An unchanged draw can reuse the prior descriptor/allocation while its draw parameters
continue to select the valid constant offset. Therefore a logger placed only in
`upload_transform_constants()` is incomplete. Capture must happen for each emitted
draw after draw-clause dependencies have updated the guest register bank.

## 6. Vertex-program identity

RPCS3 has three useful but different identities:

- `[SOURCE]` `VertexProgramBase::id` is assigned by
  `program_cache::search_vertex_program()` in `ProgramStateCache.h`. It is a cheap
  session-local serial, not stable across runs.
- `[SOURCE]` `get_vertex_program_ucode_hash()` in `ProgramStateCache.cpp` hashes the
  active normalized instruction stream.
- `[SOURCE]` `vertex_program_storage_hash::operator()` combines the microcode hash
  with program properties such as control/output/texture state and is the hash used
  by the vertex-program cache together with an exact comparator.

No finite hash should be described as a mathematically unique draw identifier. The
inspector should emit:

- session `vp_id` for cheap grouping;
- stable `vp_ucode_hash`;
- cache-equivalent `vp_storage_hash`;
- program properties, entry/base and active length;
- `constant_ids` and `has_indexed_constants` once per shader record;
- optionally the active normalized microcode bytes or a strong digest when a
  collision-safe cross-run join is required.

Draw identity is composite: capture/frame ordinal, logical draw ordinal, subdraw,
vertex-program identity, optional fragment-program identity, render-target identity,
primitive/count signature, and render state. Shader hash alone is not a draw identity.

## 7. RSX Stereo Inspector: smallest useful capture

The inspector is a discovery tool, not the stereo implementation. Its native-3D
capture answers "what did WipEout change between its known-good eyes?" A corresponding
2D/60-fps capture then answers "where do those same program families and camera inputs
exist in the single-view route?" The output needed for implementation is a mapping from
2D draws to proven camera constants and draw classes.

### Proposed event model

Use a bounded, versioned, one-frame capture with a header, shader records emitted once,
and draw events. JSON Lines is sufficient for the first spike if raw constant bits are
preserved; the storage format should not be coupled to the future VR architecture.

Capture header:

- schema version, RPCS3 commit, title ID/version;
- capture frame number and display-buffer offset/pitch;
- resolution ID, individual eye dimensions, and `avconf.stereo_enabled`;
- active host stereo presentation mode.

Per-shader record:

- the identities and exact metadata listed in section 6;
- original guest `constant_ids`;
- dynamic/indexed-addressing flag.

Per emitted draw/subdraw:

- capture frame, logical RSX draw ordinal, subdraw index, Vulkan draw-command count;
- vertex-program identities and optional fragment-program identity;
- primitive type, indexed/non-indexed mode, vertex/index counts and clause ranges;
- all color RT guest addresses, depth address, pitches, dimensions, formats, target,
  anti-aliasing and write masks;
- viewport/scissor, depth range/test/write, blend enable/mode, and draw order;
- constants used by a static shader, stored as original guest index plus four raw
  `u32` values and decoded floats;
- all usable constants for a dynamically indexed shader, explicitly marked as a
  conservative bank capture;
- global stereo state and a per-draw `eye = unknown` field;
- optional derived display-buffer relation, clearly marked `inferred`.

Raw `u32` values are authoritative. Float text alone can lose NaN payloads and exact
bits and makes capture comparison unnecessarily fragile.

### Exact instrumentation seams

1. `[INFERENCE]` Add an isolated capture writer/state object under
   `rpcs3/rpcs3/Emu/RSX/Capture/`, default off and bounded to one requested frame.
   Keep the schema backend-neutral, but wire only Vulkan for this milestone.
2. `[SOURCE -> INFERENCE]` Arm/reset/finalize it at the frame boundary represented by
   `rsx::thread::on_frame_end()` in `RSXThread.cpp`, following the existing one-shot
   frame-capture lifecycle rather than inventing an unbounded logger.
3. `[SOURCE -> INFERENCE]` Assign the logical draw ordinal in `VKGSRender::end()`.
   Emit the actual record in `VKGSRender::emit_geometry()` after dependencies and a
   successful vertex-data upload, before `vkCmdDraw*`. At that point program, constants,
   framebuffer layout, and subdraw state all correspond to the draw which will execute.
4. `[SOURCE -> INFERENCE]` Read constant data from the pristine
   `method_registers.transform_constants` bank using `m_vertex_prog->constant_ids`;
   do not reconstruct it from compacted host-buffer offsets.
5. `[INFERENCE]` Compute display-buffer overlap as offline/derived metadata. Do not
   copy `present_surface_info::eye` into draw records: it is later presentation state
   and would create false confidence.

The existing `frame_trace_data::draw_state` in
`rpcs3/rpcs3/Emu/RSX/Capture/rsx_trace.h` is not presently sufficient: the generic
capture path does not populate the requested Vulkan program/constant/RT detail.
Existing `.rrc.gz` FIFO capture can be a useful cross-check for constant writes and
frame boundaries, but it is not a replacement for resolved per-draw records.

- a bone, shadow, reflection, post-process, or object matrix can look matrix-shaped;

## 9. Falsifiable WipEout hunt

### Baseline capture

Hypothesis: WipEout renders structurally paired native-eye passes. At least one reused
vertex-program family reads a small constant block whose repeatable left/right delta
encodes the camera/view-projection change.

Control: a deterministic stationary scene with native 3D enabled, no perturbation,
and a single-frame capture. Repeat from the same save state. Capture the same scene in
ordinary 2D/60-fps mode. The native pair establishes the eye-dependent delta; the 2D
capture identifies the single-view draw and constant state which the new renderer must
amplify.

Variable: first, native 3D on versus off. Later, one candidate shader and one original
constant/component or four-slot block at a time.

Decision rule:

1. Cluster targets by guest RT/depth identity and draw order.
2. Pair draws using program content, primitive/count/range signature, nearby order,
   and render state. Do not pair on session draw ID or shader hash alone.
3. Find original constant windows whose left/right deltas repeat over many world draws
   while object-varying constants continue to vary independently.
4. Prefer candidates which feed clip-space position and have plausible matrix structure;
   translated-shader dataflow back from the position write is a required confirmation,
   not an optional heuristic.
5. Reject candidates confined to shadow/reflection/offscreen passes, bone palettes,
   HUD-only draws, or dynamically indexed banks until separately understood.
6. Map the surviving native-stereo program/pass family back to the 2D/60-fps route.
   A constant which exists only in the 30-fps native path is useful evidence but is not
   yet an injection seam for the intended renderer.

### Perturbation phase, after capture proof

`[INFERENCE]` Perturb only the transient constant copy, never
`method_registers.transform_constants`. Gate by title, stable program identity, original
guest slot, capture/pass class, and an explicit debug option. Cover both ordinary and
instanced constant-buffer construction.

Use small reversible yaw/pitch/roll and X/Y/Z translation probes with:

- a positive control proving the selected draw/slot was reached;
- an adjacent-slot or non-camera negative control;
- one changed variable per run;
- separate left/right target groups only after their provenance is supported.

Success is not merely that geometry changes or collapses. The expected world geometry
must move coherently, HUD/2D draws must remain appropriately stable, native paired-pass
structure must remain intact, and matrix/depth behavior must be consistent with the
claimed camera role.

## 10. Minimal patch sequence

1. **Capture schema and gate only.** Add a default-off, one-shot, one-frame writer and
   record the header/schema version. No OpenXR, reprojection, or presentation changes.
2. **Vulkan draw capture.** Add logical/subdraw ordinals and emit the section-7 record
   from `VKGSRender::emit_geometry()`. Emit shader metadata once per exact program key.
3. **Offline comparison tool.** Pair likely left/right target clusters and report
   constant deltas by original RSX index. Preserve ambiguous candidates instead of
   forcing an eye label.
4. **Runtime validation.** Capture repeatable WipEout native-3D and 2D frames, verify
   target/address hypotheses against the final packed buffer, and refine the draw
   classifier using evidence.
5. **Perturb the 2D/60-fps route.** Modify a transient constant copy for one selected
   shader/slot/pass and prove that yaw/pitch/roll and X/Y/Z changes move the correct
   world geometry. Cover ordinary and instanced constant construction and run all
   causal controls in section 9.
6. **Profile the proven result.** Store title ID, exact program identity, guest slots,
   transform route, draw classification, HUD policy, and evidence provenance as
   per-game data.
7. **Build a two-eye proof of concept from one 2D guest frame.** For classified world
   draws, preserve the guest state and issue two host renderings with separate transient
   left/right camera transforms and separate eye targets. Keep guest FIFO progression,
   simulation, and frame accounting single-shot. Treat HUD, shadows, reflections,
   post-processing, queries, and feedback passes explicitly rather than blindly
   duplicating every Vulkan command.
8. **Establish correctness before optimization.** A render-twice prototype is the
   clearest proof path. Once correct, assess Vulkan multiview as an optimization. The
   current RPCS3 Vulkan renderer has no general RSX multiview stereo-amplification path,
   so this is new renderer infrastructure either way.
9. **Add OpenXR only after two independently rendered eyes are correct.** OpenXR is the
   consumer of the eye images, not the mechanism that creates stereo geometry.

## 11. Open questions requiring runtime evidence

- Does WipEout render directly into the two final frame-pack ranges, use distinct
  offscreen eye targets, or compose a combined target late?
- Are eye passes adjacent, whole-scene sequential, or interleaved by pass type?
- Which programs write the primary world G-buffer/color pass, and are any important
  constants dynamically indexed?
- Is the useful camera representation projection, view-projection, or per-object WVP?
- Does the 2D/60-fps path retain the same shader families and constant layout?
- Can the 2D camera representation be separated from per-object world transforms, or
  does it require a per-draw reproject-on-clip route?
- Which RSX effects can safely be rendered per eye, which must run once and be shared,
  and which need an eye-aware composite?
- How should occlusion queries, conditional rendering, transform feedback, render-target
  feedback, and draw statistics behave when one guest draw becomes two host draws?
- Are reflections, shadows, particles, HUD, and post-processing duplicated per eye or
  shared/composited?

These are the next evidence gates. The source trace identifies where to measure them;
it does not justify answers in advance.
